# Threat model: AppAttic

Last reviewed: 2026-10-01.

No owner or review cadence is published. This file is the living model of the attack surface. Point fixes belong in application code reviews, not here.

AppAttic is a local cleanup utility (CLI `appattic`, macOS AppKit UI, Linux Qt 6 UI, Zig WASM scan core). It is not a network service. There is no login, tenant isolation, or remote API. The process runs as the OS user who launched it. The blast radius is that user's files, packages, and any privilege those package managers can obtain (polkit/sudo).

## Risk-ranked summary

| Rank | Risk | Boundary | Impact | Existing control | Gap |
|---|---|---|---|---|---|
| 1 | A generated `/bin/sh` script runs `rm -rf`, `brew uninstall`, `flatpak uninstall -y`, distro `purge`/`-Rns`, language-global removals (`npm -g uninstall`, `pipx uninstall`, `uv tool uninstall`, `pip uninstall -y --user`, `deno uninstall --global`, `pnpm`/`bun remove -g`), or `snap remove --revision` against scan results | User → app (script execution) | Permanent loss of apps, leftover data, packages, or developer tooling | UI confirm dialog when `confirmDelete` is true; interactive CLI `update` prompt; `shellQuote`; a present-check guard in front of every package removal; KEEP/system leftovers excluded from default CLI dry-run; Qt refuses a plugin command carrying shell metacharacters (`finding.cpp:585` `commandIsShellSafe`, `main.cpp:2848` `scriptLine`) | Non-interactive CLI `update` deliberately proceeds without a prompt. UI confirm can be turned off. Scripts are the only gate between a bad finding and a destructive argv, and the set of removals behind that one gate is larger than the documentation implied (see boundary 3). The script inherits `cleanupPathDirectories()` ahead of `PATH` (`Process.swift:123` `augmentedProcessEnvironment`, `Paths.swift:270` `cleanupPathDirectories`), so `rm`, `pkexec`, and `sudo` inside a confirmed script resolve from `~/.local/bin` and `~/bin` first. `rootcmd` (`Cleanup.swift:430` `withRootCmd`) is what turns a fake `pkexec` into root. |
| 2 | Disk page trashes any path the walk reached, with no packaged-path filter | Qt disk page → filesystem | Irreversible loss of arbitrary files, including `/etc` children, after a "Move to Trash" confirm | One `QMessageBox` confirm; walk is one-filesystem by default | `trashSelected` calls `QFile::moveToTrash` on the selected node with no `isProtectedPackagedPath` check and no scope limit, and `scanFilesystem` starts the walk at `/` (`diskpage.cpp:657` `scanFilesystem`, `:910` `trashSelected`, `:918` `QFile::moveToTrash`). The `/usr` deny used for leftover `rm` (`finding.cpp:528`) does not apply here at all. |
| 3 | Scan cache or WASM plugin JSON is treated as a trusted finding list and becomes cleanup commands | Build/runtime plugins; cache file → app | Attacker-chosen paths or package names in the script the user is asked to run | Cache fingerprint + 24h age and owner-only mode (`Cache.swift:161` `isScanCacheStale`, `Cache.swift:140`). WASM `host.exec` query allowlist (`hostexec.c:199`). Qt drops `rm` of `/usr`, `/etc`, `/System`, and friends (`finding.cpp:528` `commandRemovesProtectedPath`) and refuses metacharacters (`finding.cpp:585` `commandIsShellSafe`). Cache and settings are owner-only, so a cache edit needs the same user. | Cache has no MAC. Plugin `.wasm` is unsigned, and the plugin list is a `*.wasm` glob of the core-out directory, so any file dropped there is loaded (`corehost.cpp:170` `pluginWasmFiles`). `APPATTIC_HOST_EXEC_LIVE` downgrades the macOS fixture default to live `execvp` (`hostexec.c:626` `use_fixture`), and a plugin command made only of allowlisted bytes runs verbatim. Both script writers skip packaged prefixes, so a plugin `rm` cannot reach `/usr`, and only `/etc/apt/sources.list.d` rows are re-permitted past that filter, on purpose, which is what makes them prompt for root (`Cleanup.swift:357` `isProtectedPackagedPath`, `Cleanup.swift:385` `isPpaSourcesPath`, `core/src/apt.zig:204`). |
| 4 | Leftover classifier lists a credential or config tree as orphaned (`rm -rf ~/.mozilla` and similar) | Filesystem → leftover model | Secret loss | `linuxSystemNames` marks `aws`, `docker`, `kube`, `ssh`, `gnupg`, `npm`, `cargo`, `rustup`, and also `m2`, `gradle`, `java`, `maven` as `system`, and `classify` compares the dot-stripped name, so `.aws`/`.ssh`/`.gnupg`/`.m2`/`.gradle`/`.java` stay out of the script (`core/src/linux-system-names.txt`, `Identity.swift:52` `linuxSystemNames`, `Identity.swift:216` `classifyLinuxSystemName`, `Paths.swift:106` `norm` strips the dot) | `mozilla` and `thunderbird` are scanned home leaves with no entry in the system-name set. They classify `owned` only when a discovered app normalizes to `firefox`, which is the sole key that maps to `mozilla` (`Identity.swift:6` `appAliases`); `thunderbird` has no alias at all. A store or Flatpak build of Firefox or Thunderbird is not discovered under that name, so `.thunderbird` classifies `orphaned` and the default script emits `rm -rf` of a tree holding `logins.json` / `key4.db`. |
| 5 | Dangling container volumes are listed as orphaned and removed (`docker volume rm <name>`) | Package manager → cleanup script | Irreversible loss of container volume data (databases, uploads) | Volume and container identifiers are validated before they become an argument (`core/src/container_runtime.zig:87` `parseDanglingVolumes` → `isSafeIdent`, `isSafeImageId`), and the build cache row is `review` with `command: null` | The query is `volume ls -f dangling=true`, which means "no container references it", not "empty". A stopped database container leaves exactly that state, so the row is offered for deletion on the default path (`core/src/container_runtime.zig:207`), and the plugin script the operator confirms runs the removal. The Linux Zig plugin only; the Swift CLI has no container runtime scan. |
| 6 | `host.exec` is the only host import; a bug there is WASM breakout to process spawn | WASM guest → host | Arbitrary subprocess if allowlist fails | Allowlist + metacharacter reject + destructive-token deny (`hostexec.c:199` `appattic_host_exec_allowed`, `:50` `destructive_token`, `:178` metacharacter reject in `parse_argv`). No WASI filesystem. 60s cap per spawn, own process group, SIGTERM then SIGKILL to the group (`hostexec.c:30` `HOST_EXEC_TIMEOUT_MS`, `reap_child:977`). | No Wasmtime fuel/epoch, so a spinning guest is bounded only by the operator cancelling. `APPATTIC_CORE_OUT` loads whatever `.wasm` files are there. `APPATTIC_HOST_EXEC_LIVE` is checked before the Darwin default (`hostexec.c:626` `use_fixture`), so on macOS it turns the shipped fixture mode into live `execvp` for the whole core, and `flatpak-spawn --host` forwards the rewritten `PATH` to the host (`hostexec.c:1082`). |
| 7 | Outdated / brew / Flatpak talk to the network; answers are parsed as versions and names | App → internet | Wrong upgrade target; attacker who owns the tap/index influences `brew upgrade` / `flatpak update` | Untrusted Homebrew casks listed, not updated (`BrewInfo.swift` `refusedCasks`, `Outdated.swift` `applyUntrustedCasks`). Named distro upgrades run only after confirm as `/bin/sh`, never via `host.exec`. App Store stays report-only. `HOMEBREW_NO_AUTO_UPDATE=1` for a resolved `brew` binary (`Process.swift:433`). | iTunes lookup is HTTPS with no pinning (`Outdated.swift:946` `itunesRequest`). Package-manager stdout is trusted JSON/text. |
| 8 | Build scripts download toolchains | Build → runtime | Compromised zig/wasmtime/Swift/linuxdeploy becomes the binary you ship | SHA-256 pins in `scripts/dep-checksums.sha256` for Zig, Wasmtime, Swift, linuxdeploy, linuxdeploy-plugin-qt, appimagetool, each verified before use. Dockerfiles copy that file and `verify-sha256.sh` next to `linux-deps.sh` before `--install`. `scripts/deps.sh check` runs in `scripts/lint.sh` and fails if a pin, a download URL, or a Flatpak `sha256:` drifts. | No GPG. `swift:5.10.1-jammy` is tag-pinned (and checked against `.swift-version` by `scripts/deps.sh check`), not digest-pinned. `archlinux:base-devel`, the FROM in `Dockerfile.arch` and the `archlinux` job container in `linux.yml`, carries no version at all: it is a rolling tag, so that job's distro layer is whatever Arch ships that morning. The distro package layer (Qt 6, cmake, ninja, clang, patchelf, shellcheck) is not hashed at all, and `linux.yml` runs the checked-out tree as root in a container on every `pull_request`. The Flatpak runtime is pinned by branch only (`org.kde.Platform//6.10`, with `org.kde.Sdk//6.10` for the build; `scripts/deps.sh check` fails when the manifest drops or mismatches either branch), not by commit digest, so the same branch name can name different bytes across two builds, and `deps.sh` fails only when the manifest drops the branch, not when the branch moves. The AppImage's Qt libraries are collected off the build host by `linuxdeploy-plugin-qt` and appear in neither the checksums nor the SBOM, so a Qt library change reaches a released AppImage with nothing in the inventory recording it. Every shipped WASM module is built twice under a different locale, timezone and `SOURCE_DATE_EPOCH` and the two must be byte-identical, with the module list read out of `core/build.sh` rather than restated (`scripts/verify-reproducible.sh`, `repro_modules`), so a build that leaked a path or a hash-map order into any plugin fails the gate instead of shipping. That is a reproducibility control, not an authenticity one: it says the artifact is not host-dependent, not that it is the artifact a reviewer read. |

No TCP/HTTP listener, webhook, or `serve` command. `parseCLIArguments(["serve"])` is an unknown command (`CLIParse.swift`, `ScanTests.swift`).

### Not present

No HTTP server, no RPC, no message consumer, no webhook, no scheduled job inside the app, no IPC *server*, no admin port, no debug endpoint in the shipped binaries. `--smoke` is a Qt widget smoke test (`ui/linux-qt/smoke.cpp:256` `runSmoke`), not a network probe. The one IPC *client* surface is the Flatpak session bus and the file-manager portal, granted by the manifest (see boundary 7).

### Build and CI surface

`scripts/linux-deps.sh` and `scripts/linux-appimage.sh` fetch Zig, Wasmtime, linuxdeploy, linuxdeploy-plugin-qt, appimagetool, and the Swift tarball; `Package.swift` pulls `swift-cross-ui` at an exact version, and on the platform that declares it (macOS) `scripts/deps.sh` requires a `Package.resolved` carrying the resolved revision; the Linux manifest declares no package, resolves nothing, and writes no lockfile. The hashed subset is listed under boundary 8. Two things are not covered by any pin: the distro package layer (Qt 6, cmake, ninja, clang, patchelf, `shellcheck`) installs from whatever mirror the runner trusts, and `linux.yml` runs `on: pull_request` in a `swift:5.10.1-jammy` / `archlinux:base-devel` container as root over the checked-out tree. It is bounded by `permissions: contents: read`, `persist-credentials: false`, and SHA-pinned actions (`.github/workflows/linux.yml:8` `permissions`, `:26` `persist-credentials`). `release.yml` runs on tags and `workflow_dispatch` with `contents: write`; its `VERSION` is passed as an env var, not interpolated into a shell line. `Dockerfile` and `Dockerfile.arch` have no `USER` directive.

## Trust boundaries and data flow

### 1. User → app (no authentication)

There is no app identity. Whoever can run `appattic` or the UI is the operator. Confirmation is a UI setting, not authn.

Privilege transition: the process is the user. Generated scripts call `pacman`, `apt-get`, `dnf`, `zypper`, `snap`, `flatpak`, `brew`, `launchctl bootout` (`Cleanup.swift` `leftoverRemoveCommand`, `Packages.swift` `packageRemoveCommand`). Those tools may prompt for root. AppAttic never spells `sudo` itself, but it emits `rootcmd`, which does `$(id -u)`, `command -v pkexec`, then `sudo "$@"` or `pkexec` (`Cleanup.swift:430` `withRootCmd`), so the privilege step is delegated to whatever `pkexec` the script's `PATH` finds first.

That `PATH` is AppAttic's own: both Swift script runners go through one shared entry point, `runGeneratedScript`, which hands `/bin/sh` the environment from `augmentedProcessEnvironment` (`Process.swift:576` `runGeneratedScript`, `:572` `process.environment`, `:123` `augmentedProcessEnvironment`), which puts `cleanupPathDirectories()` ahead of the inherited value, and that list contains `~/.local/bin` and `~/bin` before `/usr/bin` (`Paths.swift:270`). A `pkexec` or `rm` in either directory is what a confirmed script runs. This is the sharpest undocumented boundary in the project: the script is the trust boundary, and the script's own `PATH` is attacker-writable.

CLI `--include-system` can only turn *on* including OS apps; it cannot turn a true `settings.json` value off (`Settings.swift` `effectiveIncludeSystem`).

### 2. App → filesystem (home and system inventory)

Scan roots are user XDG/Library trees plus listed home dots (`Leftovers.swift` `scanRootsForPlatform`, `homeDotData`), and the XDG roots come from the environment, so they are whatever the user or a launcher points them at.

The disk page is a second, wider door into the same filesystem. `appattic disk <path>` and the macOS "Folder path" field scan the path as given, validated only as an existing directory (`DiskUsage.swift:193` `validateDiskRoot`); the Qt page can walk `/` outright and can walk a gvfs/sshfs/SMB mount, choosing `XDG_RUNTIME_DIR/gvfs`, else `~/.gvfs`, else `/mnt` as the chooser's start (`diskpage.cpp:657` `scanFilesystem`, `:654` `scanRemote`). Nothing on this path is limited to home. Overlay scan also looks at `/usr/bin` and similar as *package* dirs to detect shadows, and both script writers refuse to `rm` a packaged prefix: Qt `isProtectedPackagedPath` (`ui/linux-qt/finding.cpp:509`) and the Swift copy of the same root list (`Cleanup.swift:357`), which also treats a `..` segment as protected because the quoted path would resolve past the prefix. One packaged prefix is deliberately reachable anyway: `/etc/apt/sources.list.d` rows come back as `review` findings (`core/src/apt.zig:204`) and `isPpaSourcesPath` re-permits them past both filters (`Cleanup.swift:385`, `ui/linux-qt/finding.cpp:677`), so a root-prompting `rm` under `/etc` is a first-class output, not an accident.

### 3. App → package managers (stdout is data)

`runCommand` / `host.exec` collect text. Parsers (`parseBrewOutdatedJSON`, `parsePacmanOrphans`, `parseAptAutoremove`, plugin JSON) turn that text into names that later become `shellQuote(name)` in uninstall/upgrade lines. A compromised `brew` on `PATH` is a compromised inventory, and `whichCommand` looks in `~/.local/bin`, `~/bin`, `~/.bun/bin`, `~/.cargo/bin` before `/usr/bin` (`Process.swift:13`), so a user bin dir wins even when `PATH` does not list it early.

The removal set is wider than the upgrade set, which is where a name from stdout does the most damage. `packageRemoveCommand` emits a guarded removal for every one of these managers, so each contributes an `uninstall`/`remove` line to the confirmed script (`Sources/AppAtticScan/Packages.swift:109`): `pacman -Rns`, `aur`, `apt-get purge -y`/`dpkg`, `dnf remove -y`, `yum remove -y`, `zypper --non-interactive rm`, `npm -g uninstall`, `pnpm remove -g`, `bun remove -g`, `pipx uninstall`, `uv tool uninstall`, `pip uninstall -y --user`, `deno uninstall --global`. The Linux Zig plugins write the same guarded lines independently for the language managers (`core/src/pip.zig:128`, `core/src/uv.zig:64`, and the `npm`/`pnpm`/`bun`/`pipx` plugins), and the Snap plugin emits `snap remove <name> --revision <rev>` behind a `test -e /var/lib/snapd/snaps/...` guard for disabled revisions and orphan `~/snap` dirs (`core/src/snapd.zig:158`, `core/src/guarded_remove.zig:31` `writeWholeGuard`). What is genuinely report-only is narrower, and the distinction is upgrade-only versus removal: `outdatedIsUpdatable` (`ui/linux-qt/finding.h`) and the plugin's own `updatable` flag keep App Store, Snap, and the language globals out of the *upgrade* script (`updateScript()` skips `!f.updatable`, `ui/linux-qt/main.cpp:2885`), and several of them are still removable. Only the App Store (no removal path at all), `gem` (upgrade-only and no removal row; `core/src/gem.zig:132` asserts no `gem uninstall` is ever emitted), and `composer` (`core/src/composer.zig:61`, same shape) are removable by nothing. `gem` and `composer` still carry a `command` string on the finding, and what keeps it out of the script is the `updatable: false` flag, not the absence of the string.


Container runtimes are a third source of the same kind. `docker` / `podman` list output becomes findings whose `command` is `<engine> volume rm <name>` or `<engine> rmi <id>`, and the engine decides what "dangling" means: `volume ls -f dangling=true` selects volumes no *running* container references, so a volume holding a database for a stopped container is a deletion candidate the operator sees as junk. The argument is identifier-validated, so the text cannot inject; the classification can still be wrong about intent (`core/src/container_runtime.zig:87` `parseDanglingVolumes`, `:181` `renderCtr`).

### 4. App → internet

- macOS App Store outdated: `URLSession` to `itunes.apple.com/lookup` (`Outdated.swift`).
- Homebrew and Flatpak commands may hit their own CDNs when `update` runs, and during `brew outdated` / `flatpak` queries.
- No other in-process HTTP client.

### 5. Plugin WASM → host

Plugins import only `host.exec` (`embed.c` `wasmtime_linker_define_func`). Default Wasmtime engine: no WASI, so no direct open/read of the host FS. Findings JSON is copied out and parsed by Qt (`finding.cpp` `appendFindingsFromBlob`). `command` / `updateCommand` fields flow into the script.

Linux default: live `execvp` (`hostexec.c` `use_fixture`). Darwin default: fixtures.

### 6. Secrets → code

AppAttic does not store service credentials. It *reads* user files that may contain them (`.aws`, `.docker`, `.kube`, `.ssh`, `.gnupg`, plus the mail and build trees listed under risk 4; shell history for usage) and can print any of it through `--json FILE`, `config`, and the cache. `settings.json` and `last-scan.json` are written atomically and then owner-only: `restrictPrivateDataFile` sets `0600` and `0700` on a parent directory named `appattic` (`FilePermissions.swift:51` `restrictPrivateDataFile`, called from `Settings.swift:358` and `Cache.swift:114` `prepareStateDirectory`). Generated temp scripts are owner-only too: Swift writes them with `writeOwnerOnlyFile` (`Process.swift:591` `runGeneratedScript`), Qt with `QTemporaryFile`, which creates the file exclusively, then narrows it to `rwx` for the owner (`ui/linux-qt/scriptproc.cpp:140` `ScriptProcess::prepare`, `:142` `QTemporaryFile`). `--json FILE` is written with `writeOwnerOnlyFile` too, but through a caller-supplied path, so the parent directory is not the appattic one (`AppAtticCLI/main.swift:219`).

Both runners now close the shared-temp-directory window, and the window used to be real. `writeOwnerOnlyFile` does not write-then-chmod: it `mkstemp`s a dot-prefixed sibling name, which is created at `0600` and fails if the name is taken, writes the bytes, `fsync`s the file, and only then renames it into place, so a reader sees either no file or the final private one and there is no umask-mode interval to win (`FilePermissions.swift:70` `writeOwnerOnlyFile`, `:76` `mkstemp`, `:113` `rename`). The Qt runner creates its file with `QTemporaryFile`, which is exclusive by construction (`ui/linux-qt/scriptproc.cpp:142`). What remains is exposure of the final name: `appattic-script-<UUID>.sh` sits in the world-writable temp directory, and a same-host account can see that a script is about to run and when. It cannot read the content, edit it, or substitute it, because the rename publishes the finished `0600` file.

### 7. Flatpak sandbox → host

The Linux Flatpak build is confined as far as the app's own behavior needs. `finish-args` grants `--filesystem=host:ro` (read on every host path, no write), `--share=ipc`, `--talk-name=org.freedesktop.Flatpak`, `--talk-name=org.freedesktop.FileManager1`, `--socket=wayland`, `--socket=fallback-x11`, `--device=dri` (`packaging/flatpak/org.appattic.AppAttic.yml` `finish-args`). The grant is read-only because no in-sandbox code path writes to a host path: settings and the scan cache go to `$XDG_DATA_HOME`, which Flatpak redirects into the sandbox, and the generated script is written to the sandbox temp directory. Two things leave the sandbox and run on the host. `host.exec` does, for its allowlisted queries, carrying `PATH` with it (`hostexec.c:1082`). And the confirmed cleanup, update, and mark-manual scripts do: `ScriptProcess::start` spawns `flatpak-spawn --host -- /bin/sh` and pipes the script in on stdin (`scriptCommand` in `ui/linux-qt/scriptproc.cpp`), because the script's own path is inside the sandbox temp directory the host cannot open, and because a removal run in-sandbox would fail against the read-only grant. That second crossing is the one that makes the grant honest, and it is the one that carries the whole destructive surface: for the length of a confirmed run, everything the script does happens on the host outside the sandbox. The script inherits `QProcessEnvironment::systemEnvironment()`, which inside a Flatpak is the *sandbox* environment, so `rm` and `pkexec` inside it resolve on the sandbox `PATH` and not on the host login session's; the crossing carries the sandbox `PATH` onto the host rather than adding the host's. `moveToTrash` leaves through the file-manager portal.

The macOS build has no equivalent confinement: `packaging/Info.plist` declares no `com.apple.security.app-sandbox` and no hardened-runtime exceptions, and `build.sh` only ad-hoc signs. An unsandboxed macOS app is bounded by the login session, which is a wider blast radius than the Flatpak description implies for the same scan.

### 8. Build → runtime

Pinned SHA-256 for Zig, Wasmtime C API, Swift Linux tarball (x86_64 and aarch64), linuxdeploy, linuxdeploy-plugin-qt, and appimagetool (`scripts/dep-checksums.sha256`, `verify-sha256.sh`), checked with `verify_sha256` before each archive is unpacked or AppImage is run. `scripts/deps.sh check` keeps those pins, the download URLs in the scripts, and the `sha256:` fields in `packaging/flatpak/` in agreement, and fails when a script, a manifest or a workflow spells a Zig or Wasmtime version other than the pinned one, or when CI installs a `uv tool` without the exact version `scripts/deps.sh` declares. Zig is installed from the checksummed tarball on every distro, so no unpinned package manager can supply the compiler. `scripts/deps.sh sbom` writes a CycloneDX 1.5 inventory of those artifacts, of the `Package.resolved` pins, of the Flatpak runtime the bundle carries, and of the vendored third-party files in the tree next to each release artifact; every component that is compiled into a shipped binary carries its SPDX licence id, so the vendored entries and the Swift package pins alike (the table is `VENDORED` and `SWIFTPM_LICENSES`, and `check` fails in both directions when a pin, a vendored file and its licence row stop agreeing), each component's purl carries the namespace and qualifiers that make it unique (a Swift package names its host and owner, a per-architecture download carries `?arch=`), so no two components are the same key to a consumer or a scanner, and the Michroma font's OFL text is installed to `share/appattic/licenses/` by `ui/linux-qt/CMakeLists.txt` because the font itself is compiled into the Qt resource. The one non-permissive grant in that set is `jpeg` (SwiftCrossUI pulls it in through `swift-image-formats`), MPL-2.0, and it is file-level copyleft: modifying that package's own sources obliges the modified files to stay MPL and to be offered in source, and says nothing about the licence of the binary that links it. No Swift package in the set is vendored or patched here, so no file it ships is modified and the obligation does not currently arise; it would arise if a build ever patched the package, and the row is recorded so that is a question the inventory answers rather than a surprise. The runtime is the one component with no hash: `flatpak build-bundle` puts the runtime in the bundle, nothing here fetches its bytes, and the manifest pins it to a branch, so the component carries `appattic:pinned-by: branch` instead of a digest nothing could check. macOS app is ad-hoc codesigned (`build.sh` `codesign --force --sign -`). AppImage is not signed in-tree. Docker base images are version tags, not digests.

| Asset | Where it lives | If stolen / corrupted / denied |
|---|---|---|
| User leftover dirs and overlay binaries | Home, `~/Library`, XDG, `~/.local/bin` | `rm -rf` of the listed path. Wrong row → wrong delete. |
| Installed apps / brew casks / Flatpak / Snap | Paths from discover + package managers | Uninstall via generated script. Steam/CrossOver are comments, not `rm` (`Cleanup.swift`). |
| Distro packages, language globals, and disabled snap revisions | `Packages.swift` `packageRemoveCommand` / WASM plugins (`core/src/pip.zig`, `core/src/uv.zig`, `core/src/snapd.zig`, …) | `apt-get purge -y`, `pacman -Rns`, `npm -g uninstall`, `uv tool uninstall`, `pip uninstall -y --user`, `snap remove --revision`, etc. All of it is a delete, and the guarded rows come from a listing query the operator reads as a report. |
| Cloud and tool credentials on disk | `.aws`, `.docker`, `.kube`, `.ssh`, `.gnupg`, `.m2`, `.gradle`, `.java` classify `system` (`core/src/linux-system-names.txt`); `.mozilla`, `.thunderbird`, `.android` do not | Delete or disclose via `--json` / cache. The mail profiles hold `logins.json` and `key4.db`. |
| Container volume contents | Docker / Podman named volumes, reported by `volume ls -f dangling=true` | `volume rm` is irreversible for a volume with no container behind it: a stopped database leaves exactly that state, so a live dataset is a deletion candidate on the default path (`core/src/container_runtime.zig:87`). |
| Scan cache and settings | `last-scan.json`, `settings.json`, `settings.json.bak`, and the legacy `AppAttic.conf` while one survives | Hide leftovers (ignore list), skip confirm, poison findings. Read: the ignore list is a list of the account's own full paths, and the snapshot is every path under the home directory, so these files are the account inventory in the clear. `appattic erase` takes the snapshot off the disk and leaves the other two. |
| Host `PATH` binaries | `whichCommand` for scan queries; `augmentedProcessEnvironment` for the generated script | Fake `brew`/`flatpak` during scan or update; fake `rm`/`pkexec`/`sudo` inside a script the user already confirmed. |
| WASM modules | `APPATTIC_CORE_OUT` / `usr/share/appattic` | Fake findings and `command` strings. |

Impact is local and user-scoped, not a multi-tenant data breach. The concrete worst cases are irreversible delete of the operator's software and leftover data (including credential directories the classifier failed to mark `system`, and container volumes the engine reports as unreferenced), a trashed system path from the disk page, and a confirmed script whose `pkexec` resolved to a user-writable directory, which is the one path in this project from a local file to root.

## Threats per boundary

### User → app

- **Spoofing:** none at app layer; OS user is the principal.
- **Tampering:** `settings.json` `confirmDelete: false` removes the UI stop. `ignoredLeftoverPaths` hides real leftovers (availability of the warning, not of the files). Both are `0600` files with no integrity check, so the trust boundary is the OS account, not the file.
- **Repudiation:** no audit log of scripts that ran. Temp `.sh` is deleted after use (`Scanner.swift`, Qt `QFile::remove`).
- **Disclosure:** `--json FILE` writes the full scan (paths, versions) to an operator-chosen path (`AppAtticCLI/main.swift:219`, `:160`). Cache holds the same. `appattic config` prints the widest unredacted read the app performs without scanning anything: the state paths, the XDG roots, and every environment switch at its full value, including `FLATPAK_ID`, `APPATTIC_CORE_OUT`, `APPATTIC_HOST_EXEC_LIVE`, `ANDROID_HOME`, and `LANG` (`runConfigCommand`, `Settings.swift:181` `lines`, `:239` `configEnvEntries`).
- **Tampering (`erase`):** `appattic erase` deletes the stored snapshot with no prompt and no `--dry-run`, and it runs before settings are read, so `confirmDelete` cannot govern it (`AppAtticCLI/main.swift:168` `runEraseCommand`, which takes `CLIOptions` only and never loads `AppAtticSettings`). It takes no path from argv, so the blast radius is the one cache file, and its cost is that the next run rescans rather than reusing poisoned rows. The confirmation gate every other destructive path carries does not cover it, because the deleted state is AppAttic's own, not the user's files.
- **DoS:** `--top` is bounded; leftover measurement uses `pmap` workers and `duSize` timeouts (`Leftovers.swift`). The cache read is bounded too: `readScanCache` takes the file's size first and refuses anything past `scanCacheMaxBytes` (256 MiB) before `Data(contentsOf:)` pulls it into memory, so a file parked at that path cannot turn into an allocation the operator did not ask for (`Cache.swift:13` `scanCacheMaxBytes`, `:74` `readScanCache`). Still unbounded: the number of leftover rows, and the shell history file up to 500k lines (`Usage.swift` `maxHistoryLines`).
- **Elevation:** CLI `update` without `--dry-run` prompts when stdin is a TTY and exits 2 without one, unless `--yes` says the run is unattended (`AppAtticCLI/main.swift:515` `confirmUpdate`). Distro remove scripts may ask for root via the package manager, not via AppAttic.

### App → filesystem / leftover model

- **Tampering / elevation of “delete me”:** `Identity.classify` returns `orphaned` for unknown names (`Identity.swift:444`). Home-dot leaves are classified by their dot-stripped name, so `.aws`, `.docker`, `.kube`, `.ssh`, `.gnupg`, `.npm`, `.cargo`, `.rustup`, `.m2`, `.gradle`, `.java`, `.maven` all hit `linuxSystemNames` and stay `system`; `.mozilla`, `.thunderbird`, and `.android` have no entry and can reach the script as `orphaned` when the owning app is not discovered. A future rename of a system dir that is not on the list will show up as leftover. Default CLI dry-run includes orphaned leftovers (`Cleanup.swift` `cleanupScript`).
- **Elevation:** `isPpaSourcesPath` re-permits `/etc/apt/sources.list.d` past the packaged-path filter and the command is root-marked (`Cleanup.swift:385`, `commandNeedsRoot` `Cleanup.swift:383`), so one class of leftover delete is a root prompt by design.
- **Tampering (disk page):** `trashSelected` moves any selected node to Trash with only a dialog in front of it, including a child of `/` (`diskpage.cpp:910`). `isProtectedPackagedPath` guards `rm` in `finding.cpp:509` and the equivalent Swift path in `Cleanup.swift:357`, and nothing else: neither the Qt nor the Swift filter is reached from the disk page.
- **DoS:** `probeActivityMtime` caps entries/depth/time. `duSize` 6s timeout. The disk walk has no per-entry deadline, only a cooperative cancel (`ui/linux-qt/diskusage.cpp:66` `isCancelled`, checked per entry at `:237` and `:438`), so a hung sshfs or SMB mount blocks its worker indefinitely (`diskpage.cpp:659` `scanRemote`).

### App → package managers / internet

- **Spoofing:** `whichCommand` prefers extras then `PATH`. A user-writable directory earlier on `PATH` wins for `brew`/`flatpak`, and for `docker`/`podman`, whose queries the Zig plugin issues as bare `docker …` strings (`container_runtime.zig:22`).
- **Tampering:** `parseBrewOutdatedJSON` and friends take names from stdout. Those names are `shellQuote`d into `brew upgrade` / `flatpak update -y`.
- **Tampering (removal breadth):** the same stdout names reach the removal side, which is a delete and not an upgrade. `packageRemoveCommand` (`Sources/AppAtticScan/Packages.swift:109`) and the matching guarded lines in the language plugins turn a name from `npm ls -g`, `pnpm ls -g`, `bun pm ls`, `pipx list`, `uv tool list`, `pip show`, and a `test -e ~/.deno/bin/<name>` probe into `npm -g uninstall`, `pnpm remove -g`, `bun remove -g`, `pipx uninstall`, `uv tool uninstall`, `pip uninstall -y --user`, `deno uninstall --global`, each wrapped in a present-check guard (`core/src/pip.zig:128`, `core/src/uv.zig:64`). The Linux Snap plugin writes `snap remove <name> --revision <rev>` for a disabled revision or an orphan `~/snap` dir, guarded by `test -e /var/lib/snapd/snaps/<name>_<rev>.snap` (`core/src/snapd.zig:158`, `core/src/guarded_remove.zig:31` `writeWholeGuard`). A hostile or simply wrong stdout row in any of these is a removal line in the script the operator confirms, so the guard proves the package is *present*, never that removing it is wanted.
- **Spoofing (manager name, not row):** a fake `npm`, `pipx`, `uv`, or `docker` earlier on the resolution order is not asked for a list only; the removal half of the same tool is what the script eventually runs.
- **Tampering (container classification):** the volume and image identifiers in `docker`/`podman` output are validated before they become arguments, so the parser cannot inject. What it can do is misread liveness: `dangling=true` on a volume means "no container references it", so a stopped service's volume is reported `orphaned` and its removal lands in the default plugin script (`container_runtime.zig:181` `renderCtr`).
- **Disclosure:** iTunes description text is shown (truncated `shortDesc`). No TLS pin.
- **DoS:** `runCommand` 60s per process; iTunes 12s + 15s wait.

### WASM guest → host

- **Elevation:** only if `appattic_host_exec_allowed` returns true for a dangerous argv. Current deny includes `rm`, `rmi`, `rmdir`, `remove`, `purge`, `prune`, `upgrade`, `uninstall`, `system`, `install`, `update`, `add`, `inject`, `-y`, `--force`, and the pacman remove flags (`hostexec.c:50` `destructive_token`, applied at `:283`). A second deny covers manager config switches (`-o`, `-c`, `--config`, `--setopt`, `--root`, `--admindir`, the apt `*-invoke` family and the rest of `config_injection_token`), which a listing-shaped argv such as `apt list --upgradable -o APT::Update::Pre-Invoke::=id` would otherwise use to run a command through the shell (`hostexec.c:68`, applied at `:284`); that is a fixed class of exploit in this host shim, not a hypothetical. `parse_argv` rejects the metacharacters `; | & \` $ < >` and also `( )` and CR/LF outright, before the allowlist runs (`hostexec.c:184`). The query shapes are matched per manager, list-only, and never the remove verbs: `ls_query_ok` (`hostexec.c:87`) for `ls`, `test_query_ok` (`hostexec.c:102`) for `test`, plus single-purpose shapes for `readlink` (flags limited to `-f`/`-n`, exactly one path) and `realpath` (no flag at all, exactly one path) (`hostexec.c:237`, `:247`). The first token itself must be one of the enumerated managers, `ls`, `readlink`, `realpath`, or `test`; anything else is denied before the shape checks (`hostexec.c:228`).
- **Tampering:** plugin JSON `command` is used by Qt `leftoverCleanupCommand` after a `/usr`-rooted `rm` filter (`commandRemovesProtectedPath`), and `scriptLine` then runs it through a byte allowlist that refuses `; | & $ \`` , redirect, and newline outside single quotes (`finding.cpp:560`, `main.cpp:2848`). A plugin can still emit `rm -rf /home/user/.aws`, which passes both. Which plugins exist is a directory listing, not an allowlist (`pluginWasmFiles`, `corehost.cpp:170`).
- **DoS:** the shared engine is built with a cache config only, no fuel or epoch deadline (`embed.c:232` `shared_engine`, `wasm_engine_new_with_config`). A guest instruction loop that never calls `host.exec` runs until the operator cancels (`requestCoreWasmCancel` sets the flag the host checks between spawns, not a guest interrupt). An allowlisted spawn is capped at 60s and its process group is killed.
- **Tampering (module loading):** every export the host binds is checked for kind before it is used — a plugin `memory` export that is not a memory, and a core `plugin_abi_version` or `query` that is not a function, are skipped with `skip %s (bad plugin exports)` rather than read as handles (`core/host/embed.c` `wasmtime_extern_t`/`wasmtime_extern_delete` path in `load_plugin`, `wasmtime_caller_export_get`). ABI version must equal 1. This closes a host-side type confusion on an attacker-supplied `.wasm`, not the module set: which files load is still a directory glob, and a module that exports the right kinds with the right names is a loaded plugin.
- **Disclosure:** allowlisted `ls` / package queries return host inventory into guest memory, then into the UI.

### Flatpak sandbox → host

- **Tampering / elevation:** a loaded plugin inside the sandbox can read any host path and can write the sandbox's own `$XDG_DATA_HOME` and temp directory, but `--filesystem=host:ro` denies it writes anywhere on the real filesystem. A host write therefore needs either `moveToTrash` through the file-manager portal or a confirmed script run under `flatpak-spawn --host`, which happens outside the sandbox.
- **Tampering / elevation (the whole script):** `ScriptProcess::start` sends the confirmed script to the host through `flatpak-spawn --host -- /bin/sh` on stdin (`ui/linux-qt/scriptproc.cpp` `scriptCommand`, `scriptRunsOnHost`), so the sandbox boundary is not a control in front of `rm`, `apt-get purge`, or `flatpak uninstall` from the generated script. That is a deliberate trade for a read-only `--filesystem=host:ro` grant: the alternative is a confirmed cleanup that fails silently on every packaged path. The cost is that a compromise of the Qt UI or the core reaches the host filesystem with the operator's own authority, under the same single confirm gate, rather than being stopped by the grant.
- **Spoofing:** `flatpak-spawn --host` forwards the sandbox `PATH` to the host (`hostexec.c:1082`), so a user-writable directory that got into the in-sandbox `PATH` is also the host's resolution order for the query that runs there.
- **DoS:** a query that is allowlisted in-sandbox can be expensive on the host, where it is not bounded by the sandbox's own cgroup.

### Build → runtime / CI

- **Tampering:** every fetched tarball, AppImage, and plugin is SHA-256 verified before it is unpacked or run: Swift (`scripts/linux-deps.sh:186` `verify_sha256`, then `tar -xz`), Zig, Wasmtime, linuxdeploy, linuxdeploy-plugin-qt, appimagetool. The distro layer (Qt 6, cmake, ninja, clang, patchelf, shellcheck) is not hashed and resolves from the runner's mirror, and `Dockerfile` / `Dockerfile.arch` have no `USER` directive.
- **Elevation:** `linux.yml` runs `on: pull_request` as root in a container against the checked-out tree. Bounded by `permissions: contents: read`, `persist-credentials: false`, and SHA-pinned actions (`.github/workflows/linux.yml:8`, `:26`).
- **Repudiation / spoofing:** `release.yml` takes `contents: write` on `workflow_dispatch` and can be dispatched on a non-tag ref, so the artifact's provenance is the selected ref, not a tag. `VERSION` is passed as an env var, not interpolated into `run:`.
- **Spoofing:** ad-hoc macOS signature only (`build.sh`).

## Mitigations mapping

| Control | File | Covers | Does not cover |

### Single points of failure

1. **Operator confirmation** (a TTY prompt, or `--yes` for an unattended CLI `update`) is the control in front of every high-impact delete/upgrade, and it is one checkbox away from being off.
2. **`PATH` resolution inside the generated script** is the control in front of "the delete is the one the user read". One user-writable directory in front of `/usr/bin` defeats it, and it is the only path here that can reach root through a confirmed action.
3. **`appattic_host_exec_allowed`** is the control in front of every WASM-spawned process, and it is bypassed wholesale by one environment variable on macOS.
4. **Leftover `system` name lists** are the control in front of deleting home-dot credential trees; the list is a text file, not a rule, and the mail profiles are missing from it. `.m2`, `.gradle`, and `.java` were added to it; `.mozilla` and `.thunderbird` were not, and only a discovered app name keeps them `owned`.
5. **Engine-reported liveness** is the control in front of deleting a container volume, and it is a reference count the operator has to interpret correctly at a glance.
6. **The present-check guard** (`pacman -Qq`, `dpkg -s`, `npm ls -g`, `pip show`, `uv tool list`, `test -e ~/.deno/bin/…`, `test -e /var/lib/snapd/snaps/…`) is the only automatic control in front of every package removal, and it answers "is it installed", which is not the question that matters. One confirm now covers `rm -rf` of a home directory, a distro purge, a language-global uninstall, and a snap revision removal alike, and several of those verbs carry their own `-y` so nothing asks twice.

## Abuse cases

These are hostile-but-local scenarios. Evidence is the code path, not an exploit.

1. **Skip the confirm dialog.** Settings → `confirmDelete` false (`ContentView.swift` `confirmDeleteBinding`, Qt `m_confirmBox`). Delete/Update/Mark Manual run `runTempScript` / `runScript` on the first click.
2. **Non-interactive CLI upgrade without review.** With stdin redirected, `appattic update --yes` → `confirmUpdate` returns true on the flag → `updateScript` → `runShellScript` (`main.swift:515` `confirmUpdate`, `:532` `runShellScript`). Automation is a flag away, and the flag is the record that it was deliberate; without it the run stops at exit 2.
3. **Poison `last-scan.json`.** Write a cache with the current fingerprint, `includeSystem` matching the next run, `scanned_at` within 24h, and an extra leftover path. `resolveScan` will use it (`Cache.swift:494` `resolveScan`, stale check at `:469`). The UI/CLI then offers that path in cleanup. The file is `0600`, so this is the same user, not another account.

16. **A package name that renders as another package.** A registry, tap, or manager listing returns a name carrying U+202E RIGHT-TO-LEFT OVERRIDE, so `libfoo` + U+202E + `dwp` reads as `p w d` in the confirm dialog while the child command the dialog's checkbox produces removes something else; the zero-width and tag ranges drop letters without changing the name's length, so two packages render as one row and the row's `grep -F` matches only one. Swift strips these scalars from every name that becomes a package or outdated row (`sanitizedPackageName`, built on `terminalSafe` and `stripBidiControls`); Qt refuses any non-ASCII package name (`isSafePackageName`) and Zig refuses the row at the source (`isSafeCmdIdent`). Nothing here is a privilege boundary: a plain ASCII name that is simply wrong is still removed by a confirmed script.
17. **A Steam library VDF that points somewhere else.** `libraryfolders.vdf` names the library roots, `parseSteamLibraryFolders` returns each `"path"` as written, and `visitSteamLibraries` resolves it and walks it. The reader now strips `//` comments outside quoted runs and resolves `\"` before counting braces, so a manifest is parsed as written rather than as a comment left it; that is a parsing control, not an integrity one, and the file carries no MAC.

Client-side enforcement: the ignore list and confirm toggle are local files, not a server policy. There is no server.

## Response readiness (note only)

- Scripts run with stdout discarded (UI) and stderr kept only until the process exits; the temp file is deleted. Only the last 64 KiB of it is read back, so a long transaction cannot grow the running UI. There is no durable “what we deleted” log in-tree.
- No disclosure contact, supported-version list, or “report → fix shipped” path is published. See `SECURITY.md`.
