# Security

No dedicated disclosure contact, supported-version list, or vulnerability-response process is published for this repository.

The living attack-surface model is [`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md). Claims below are checked against the code as of that document's last-reviewed date.

## What this software is

AppAttic is a local CLI and desktop UI. It does not listen on a network port, authenticate users, or accept untrusted remote clients. It runs as the OS user who launched it and can generate `/bin/sh` scripts that delete leftover files or uninstall/upgrade packages.

It is not confined by a sandbox in either build. The macOS app declares no App Sandbox entitlement and is ad-hoc signed only (`packaging/Info.plist`, `build.sh`). The Linux Flatpak build requests `--filesystem=host:ro`, which is read on every host path and no write, plus the session bus and the file-manager portal (`packaging/flatpak/org.appattic.AppAttic.yml`). Package-manager queries and the generated cleanup scripts leave the sandbox through `flatpak-spawn --host` (`core/host/hostexec.c`, `ui/linux-qt/scriptproc.cpp`).

## What the code actually does

- **Leftovers, stale, outdated (report), packages, and disk CLI** print a report. They do not delete. `--dry-run` prints a script for the operator to review and run themselves (`Sources/AppAtticCLI/main.swift`, `Sources/AppAtticScan/Cleanup.swift`).
- **`appattic erase` is the one CLI command that deletes, and it is not gated by any setting.** It removes the stored scan snapshot (a full list of paths under the home directory) with no prompt and no `--dry-run`, takes no path from argv, and runs before `settings.json` is read, so `confirmDelete` does not apply (`Sources/AppAtticCLI/main.swift` `runEraseCommand`, `Sources/AppAtticScan/Cache.swift` `eraseScanCache`). It removes that one file: `settings.json`, `settings.json.bak`, and the legacy `QSettings` file are all left alone.
- **CLI `update` without `--dry-run`** prompts before writing and running a temp `/bin/sh` script when stdin is a TTY. Without a TTY it refuses with exit 2 unless `--yes` is passed, so an unattended run is an explicit choice; `--dry-run` is the review-only path. It upgrades Homebrew formulas/casks and Flatpak apps only (`confirmUpdate` in `Sources/AppAtticCLI/main.swift`; `updateScript` in `Sources/AppAtticScan/Outdated.swift`).
- **macOS and Linux UIs** run delete, update, and mark-manual scripts after a confirm dialog when `confirmDelete` is true (the default). The operator can turn that setting off in the UI or in `settings.json`.
- **A generated script runs with a `PATH` AppAttic chose.** `augmentedProcessEnvironment` puts `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, and `~/bin` ahead of `/usr/bin`, and both Swift script runners hand that to `/bin/sh` (`Sources/AppAtticScan/Process.swift`, `Sources/AppAtticScan/Paths.swift` `cleanupPathDirectories`, `Sources/AppAttic/Scanner.swift`, `Sources/AppAtticCLI/main.swift`). A `rm`, `pkexec`, or `sudo` in one of those directories is what a confirmed script actually runs. The Qt runner uses the session's own environment instead (`ui/linux-qt/scriptproc.cpp` `ScriptProcess::prepare`).
- **Distro removals can reach root through that `PATH`.** `rootcmd` resolves `pkexec` with `command -v` and falls back to `sudo` (`Sources/AppAtticScan/Cleanup.swift`). `/etc/apt/sources.list.d` rows are re-permitted past the packaged-path filter on purpose, so those deletes prompt for root.
- **The Linux disk page can walk `/` and can move any walked path to Trash** after a dialog, with no packaged-path filter on that path (`ui/linux-qt/diskpage.cpp` `scanFilesystem`, `trashSelected`). It can also walk a gvfs/sshfs/SMB mount. `appattic disk PATH` and the macOS folder field accept a path as given (`Sources/AppAtticScan/CLIParse.swift`, `Sources/AppAtticScan/DiskUsage.swift` `validateDiskRoot`).
- **Untrusted Homebrew casks** stay listed and are not updated (`Sources/AppAtticScan/BrewInfo.swift`, `Outdated.swift`). Named Homebrew, Flatpak, apt, pacman, AUR, dnf/yum, and zypper upgrades run only after confirm, as a reviewed `/bin/sh` script, never through `host.exec`. App Store, Snap, and the language globals have no upgrade path: their findings are `updatable: false`, which `updateScript()` skips (`ui/linux-qt/main.cpp` `updateScript`, `outdatedIsUpdatable`).
- **Report-only is about upgrading, not about removing.** The managers with no upgrade path are several of the managers that can be *removed*, and a confirmed script removes them: `npm -g uninstall`, `pnpm remove -g`, `bun remove -g`, `pipx uninstall`, `uv tool uninstall`, `pip uninstall -y --user`, `deno uninstall --global` (`Sources/AppAtticScan/Packages.swift` `packageRemoveCommand`, and the same guarded lines in the Linux plugins `core/src/pip.zig`, `core/src/uv.zig`). On the Linux Qt build the Snap plugin also emits `snap remove <name> --revision <rev>` for disabled revisions and orphan `~/snap` dirs, behind a `test -e` guard (`core/src/snapd.zig`, `core/src/guarded_remove.zig`). Only the App Store, `gem`, and `composer` are removable by nothing: `gem` has no uninstall path (`core/src/gem.zig` asserts none is emitted) and composer has no removal row. Every one of these removals still rides the single confirm gate; `pip uninstall -y` and the `uv`/`pipx` verbs carry their own `--yes`/no-prompt flag, so nothing asks twice.
- **WASM `host.exec`** (Linux Qt core) allowlists read-only package-manager queries and denies destructive argv (`core/host/hostexec.c`). Cleanup still happens in a host `/bin/sh` script the UI runs, not through `host.exec`. `APPATTIC_HOST_EXEC_LIVE=1` overrides the macOS fixture default and turns every allowlisted query into a live `execvp` for the whole core. That variable and `APPATTIC_HOST_EXEC_FIXTURE` are read as strict booleans, so writing `false` to either one leaves it off rather than on.
- **WASM modules** in the core-out directory are loaded by `*.wasm` glob and checked for ABI version 1 only. They are not signed and there is no filename allowlist, so anyone who can write into that directory controls what the core loads (`ui/linux-qt/corehost.cpp`).
- **Qt refuses a plugin command carrying shell metacharacters** before it reaches a script line (`ui/linux-qt/finding.cpp` `commandIsShellSafe`, `ui/linux-qt/main.cpp` `scriptLine`). A command made only of allowlisted bytes still runs verbatim, and the Swift CLI and macOS UI have no equivalent check on plugin-supplied text.
- **Local state and generated scripts** are owner-only from the instant they exist. `settings.json`, `last-scan.json`, and every generated script go through `writeOwnerOnlyFile`, which `mkstemp`s a dot-prefixed sibling, writes, `fsync`s, and renames into place, so nothing is ever visible at a wider mode and no name can be pre-created in the shared world-writable temp dir (`FilePermissions.swift` `writeOwnerOnlyFile`, `prepareStateDirectory`). The Qt runner creates its script exclusively (`QTemporaryFile`). What stays visible is the final script name, so a same-host account can tell that a cleanup or update ran and roughly when, not what was in it. `--json FILE` and `appattic config` write through a caller-supplied path, so the `appattic` parent rule is not applied to a directory the app did not create. Both state files are read behind `JSONSerialization` and a control-character scan, because the decoder's string unwrap aborts the process rather than throwing on either one (`Cache.swift`, `Settings.swift`, `JSONText.swift` `jsonHasNoControlCharacterInString`); that is a read-safety check, not an integrity one, and a well-formed file carrying attacker-chosen findings still passes it. The scan-snapshot read is bounded at 256 MiB on the file's size before it is loaded (`Cache.swift` `scanCacheMaxBytes`, `readScanCache`).
- **`settings.json.bak` is a second copy of the ignore list, and `erase` does not remove it.** Every settings save that changed the file writes the previous one there, owner-only on both the Swift and the Qt side, and a save whose bytes already match the backup is skipped so a repeated save cannot overwrite the older generation (`Sources/AppAtticScan/Settings.swift` `keepSettingsBackup`, called from `saveSettings`; `ui/linux-qt/settings.cpp` `keepSettingsBackup`). The Linux window's old `QSettings` file holds the same list and is narrowed to `0600` on read before the migration retires it (`ui/linux-qt/settings.cpp` `migrateLegacyQSettings`). `appattic erase` deletes the scan snapshot only, so an operator who erased the account's own paths still has the ignore list on disk in one or both of these.
- **`appattic config` is the widest read the app performs, and none of it is redacted.** It scans nothing and prints the settings path, the scan-cache path, the settings backup path, all four XDG homes, `XDG_DATA_DIRS`, `XDG_RUNTIME_DIR`, and then every environment switch the app reads at its full value with the effect that value has — including `FLATPAK_ID`, `APPATTIC_CORE_OUT`, `APPATTIC_HOST_EXEC_LIVE`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, and `LANG` (`Sources/AppAtticCLI/main.swift` `runConfigCommand`, `Sources/AppAtticScan/Settings.swift` `EffectiveConfig.lines`, `configEnvEntries`). `--json FILE` writes the same payload to an operator-chosen path. It is the output a bug report asks for, and it names where the unsigned plugin directory is and whether the core is answering from fixtures or from live `execvp`.
- **Generated scripts** quote paths and names (`shellQuote` in `Sources/AppAtticScan/ShellScript.swift`). Quoting is not a substitute for a wrong leftover classification, and `.aws`, `.ssh`, `.gnupg`, `.docker`, `.kube`, `.m2`, `.gradle`, `.java`, and `.maven` are only kept out of it by an entry in `core/src/linux-system-names.txt`, while `.mozilla` and `.thunderbird` are not: they classify `owned` only when a discovered app normalizes to `firefox` (`Sources/AppAtticScan/Leftovers.swift` `appAliases`), so a store or Flatpak mail client leaves them `orphaned`.
- **Dangling container volumes are removable by default** on the Linux Qt build. `docker volume ls -f dangling=true` (and the same for `podman`) matches any volume no container currently references, and the plugin emits `<engine> volume rm <name>` into the script the operator confirms (`core/src/container_runtime.zig` `renderCtr`). A stopped database container leaves exactly that state, so the row can carry live data. The identifier is validated before it becomes an argument (`isSafeIdent`, `isSafeImageId`), which is an injection control, not a liveness one.
- **CI** runs the checked-out tree as root in a container on every `pull_request`, bounded by `permissions: contents: read` and SHA-pinned actions (`.github/workflows/linux.yml`). The Zig, Wasmtime, Swift, linuxdeploy, linuxdeploy-plugin-qt, and appimagetool downloads are SHA-256 verified before use (`scripts/dep-checksums.sha256`, `verify_sha256` in `scripts/linux-deps.sh` and `scripts/linux-appimage.sh`); the distro package layer is not.

## Out of scope for this file
